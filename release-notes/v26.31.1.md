# v26.31.1

## Copilot CLI: hooks no longer block unrelated projects on Windows

Reported in [#42](https://github.com/data-goblin/power-bi-agentic-development/issues/42). Installing `pbip`, `pbi-desktop` or `paginated-reports` in Copilot CLI on Windows could deny every tool call in every project on the machine. Three Copilot behaviors combined: plugins are user-wide, the `if` path filters in `hooks.json` are a Claude Code feature Copilot ignores (so each hook fired on every edit and shell call), and Copilot runs hook commands under PowerShell and treats any non-zero PreToolUse exit as a denial, so a bare `bash "..."` with no Git Bash on `PATH` blocked the tool.

- Each hook-bearing plugin now carries `.github/plugin/plugin.json`, which Copilot reads ahead of the Claude manifest and which points it at `hooks/copilot-hooks.json`; Claude Code keeps reading `hooks/hooks.json` unchanged
- `copilot-hooks.json` wires the same scripts with explicit `bash` and `powershell` commands. Both exit 0 unless the script itself blocks with 2, and both are no-ops when `CLAUDE_PLUGIN_ROOT` or the script is missing
- `hooks/run-hook.ps1` is the Windows entry point: it locates Git Bash (never WSL's `System32\bash.exe`), forwards the hook JSON on stdin as UTF-8, and only ever exits 0 or 2
- `pbi-hooks.sh` gains `pre` and `post` subcommands that run every check in turn, so Copilot spawns one process per event instead of seven per shell call
- All hook scripts accept Copilot's lowercase tool names (`bash`, `powershell`, `edit`, `create`) and its `path` argument, so the checks actually run there instead of silently skipping
- `scripts/bump_release_version.py` bumps the Copilot manifests in lockstep
- README: Copilot installs are always user-wide; hooks compatibility rewritten; a recipe for the `Access is denied. (os error 5)` uninstall failure, which is an open Copilot CLI bug ([copilot-cli#4095](https://github.com/github/copilot-cli/issues/4095)) triggered by VS Code or a second CLI session holding handles on the plugin folder
